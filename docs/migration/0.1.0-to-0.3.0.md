# Migrating from 0.1.0 to 0.3.0

This guide takes a consumer of `@lhellemons/ground-types` 0.1.0 to 0.3.0
in one pass. It includes every break from the 0.2.0 release, so there is
no need to stop there on the way. Changes are organised by module;
every breaking change shows the 0.1.0 code and what it becomes.

> **Before touching any imports, read
> [Environment requirements](#environment-requirements).** 0.3.0's
> emitted type declarations reference `AbortController`, `AbortSignal`
> and `DOMException`. A project whose TypeScript `lib` is `["ES2022"]`
> alone — which compiled 0.1.0 fine — will fail to compile against
> 0.3.0 before a single API change comes into play.

Also read [`/brand`](#brand) even if nothing fails to compile after the
upgrade: the one change most likely to break an 0.1.0 consumer
_silently_ is there.

## Summary of renames and removals

| Module             | 0.1.0                                               | 0.3.0                                                          |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------------- |
| `/maybe`           | `flatMap`                                           | Renamed to `andThen` (same signature, same behaviour)          |
| `/maybe`           | `flatten`                                           | Removed — it was an identity function; delete the call         |
| `/fn`              | `Function`                                          | Renamed to `Fn` (same signature)                               |
| `/domain`          | `DomainObjectDTO`                                   | Renamed to `DTOSource` (same shape)                            |
| `/domain`          | `DomainObjectFactory<D, DTO, TExtra>`               | `E` inserted before `TExtra`: `<D, DTO, E, TExtra>`            |
| `/result`          | `failure<T, E>(e)`                                  | Parameters reordered: `failure<E, T>(e)`                       |
| `/result`          | `map<T, U, E>(fn)` / `andThen<T, U, E>(fn)`         | Two type parameters; drop the explicit arguments               |
| `/result`          | `map` with a `Result`-returning callback            | Compile error — use `andThen`                                  |
| `/result`          | `tryCatch<T, Args, E>(fn)` with no handler          | Compile error — supply the handler, or drop the type arguments |
| `/result`          | `tryCatch` handler returning an `Error`             | Still compiles — the handler now returns a `Result`            |
| `/maybe` `/result` | `map`/`andThen`/`tryCatch` with an `async` callback | Compile error — lift with `promise/resultify` first            |
| `/brand`           | Hand-rolled `as string & { __brand: 'X' }` casts    | No longer assignable — construct through the branded type      |
| `/value-object`    | `definePrimitiveValueObject<P, T>`                  | Parameters reordered and extended: `<T, P, E>`                 |
| `/value-object`    | `PrimitiveValueObject<T, P>`                        | Gains an error parameter: `<T, P, E>` (defaulted)              |

Everything else — the currying retrofit, `maybe/fromNullable`,
`result/mapError` and friends, the whole asynchrony layer, the root entry
point — is additive. See [What 0.3.0 adds](#what-030-adds).

## Environment requirements

0.1.0 declared no engine requirement and compiled under a bare
`"lib": ["ES2022"]`. 0.3.0 requires:

- **Node 20 or newer.** `package.json` now declares
  `"engines": { "node": ">=20" }`.
- **A TypeScript `lib` that includes `DOM`, or `@types/node`.** The new
  `/promise` and `/abort` modules are built on `AbortController`,
  `AbortSignal` and `DOMException` — WHATWG platform standards, present
  in browsers, Node 20+, Deno and Bun alike, but absent from
  `lib.es2022` — and they appear in the library's emitted declarations.

```jsonc
// 0.1.0 — compiled fine
{ "compilerOptions": { "lib": ["ES2022"] } }

// 0.3.0 — either of:
{ "compilerOptions": { "lib": ["ES2022", "DOM"] } }
{ "compilerOptions": { "lib": ["ES2022"], "types": ["node"] } } // with @types/node installed
```

## `/maybe`

### `flatMap` is now `andThen`

Renamed in 0.2.0 for symmetry with `result/andThen`. Same signature,
same behaviour — a mechanical rename.

```ts
// 0.1.0
import { flatMap, maybe } from '@lhellemons/ground-types/maybe'
const first = flatMap((s: string) => maybe(s.split(',')[0]))

// 0.3.0
import { andThen, maybe } from '@lhellemons/ground-types/maybe'
const first = andThen((s: string) => maybe(s.split(',')[0]))
```

(`andThen` is a true alias of `maybe/map` — a `Maybe` cannot nest, so
there is nothing for a distinct chaining form to flatten. It exists so
generic code can treat `/maybe` and `/result` alike.)

### `flatten` is removed

It was provably an identity function: `Maybe<Maybe<T>>` and `Maybe<T>`
are mutually assignable in the unboxed encoding, so nothing ever nested
and nothing was ever flattened. Delete the call and keep its argument —
no replacement is needed, and none exists.

```ts
// 0.1.0
const flat = flatten(nested) // nested: Maybe<Maybe<number>>

// 0.3.0
const flat = nested // already a Maybe<number>; the types agree
```

### `map`/`andThen` reject `async` callbacks at compile time

In 0.1.0, `map(async (n) => ...)` compiled and produced a
`Maybe<Promise<U>>` — a `Just` that is an unresolved `Promise`, present
whatever it eventually settles to. This is now a compile error naming
the fix. Lift the async operation with `promise/resultify` (or
`call/resultify`) first, then compose with `.then()`:

```ts
// 0.1.0 — compiled, but the Maybe held an unresolved Promise
const widget = map(async (id: string) => fetchWidget(id))(maybeId)

// 0.3.0
import { fail, resultify } from '@lhellemons/ground-types/promise'
import { map } from '@lhellemons/ground-types/result'

const widget = isJust(maybeId)
  ? await resultify(fail, fetchWidget(maybeId))
  : nothing()
```

## `/result`

### `failure`'s type parameters are reordered: `<T, E>` → `<E, T>`

The single explicit type argument a caller plausibly writes —
`failure<MyError>(e)` — used to bind the _success_ type, silently
demoting the named error class to plain `Error` with no diagnostic. It
now binds the error. Call sites with no type arguments are unaffected;
call sites naming both swap them:

```ts
// 0.1.0
failure<User, EmptyName>(new EmptyName())

// 0.3.0
failure<EmptyName, User>(new EmptyName())
```

`success<T, E>` keeps its value-first order — the asymmetry is
deliberate: each constructor puts the type its caller actually has in
hand first.

### `map` and `andThen` take two type parameters, not three

Both were `<T, U, E>` (input, output, error). The unapplied forms are
now generic in the _eventual_ input — `T` and `E` bind when the `Result`
is applied, not at `map(fn)` — so they take two: the callback's input
and its return type. A call site passing three explicit type arguments
no longer compiles.

The right fix is almost always to drop the type arguments entirely and
let inference bind them at application:

```ts
// 0.1.0
const label = map<number, string, MyError>((n) => `n${n}`)

// 0.3.0 — preferred: let it infer
const label = map((n: number) => `n${n}`)

// 0.3.0 — if you must name them: input and return type only
const label = map<number, string>((n) => `n${n}`)
```

For `andThen`, note that the second parameter is now the callback's
**whole return type** (a `Result`), not the success type it carries —
one more reason to drop the arguments and let inference do it:

```ts
// 0.1.0
const step = andThen<number, string, MyError>((n) =>
  n > 0 ? success(`w${n}`) : failure(new MyError()),
)

// 0.3.0
const step = andThen((n: number) =>
  n > 0 ? success(`w${n}`) : failure<MyError, string>(new MyError()),
)
```

### `andThen`'s error type widens instead of unifying

In 0.1.0, `andThen` forced the input's error and the callback's error
into a single `E`. It now produces `Result<U, E | F>` — the union of the
input's error type and whatever the callback can fail with. This is a
compile-time widening only; if you exhaustively matched on the error
type after a chain, the type now tells you about arms 0.1.0 silently
dropped. (0.1.0's `andThen` also collapsed the success type to `unknown`
for any callback with more than one return path; that is fixed, not
something to migrate.)

### `map` rejects a `Result`-returning callback

In 0.1.0 this inferred `any` and silently erased downstream type
checking. It is now a compile error whose message names the fix:

```ts
// 0.1.0 — compiled, inferred `any`
map((n: number) => (n > 0 ? success(n) : failure(new MyError())))

// 0.3.0
andThen((n: number) => (n > 0 ? success(n) : failure(new MyError())))
```

A callback returning an `Error` subclass _as a value_ is also rejected
(`'A Success can never be an Error'`). There is no combinator to reach
for there: the unboxed encoding discriminates by `instanceof Error`, so
an Error-typed success value is unrepresentable. Wrap it in a non-Error
carrier, or rethink the type — see
[ADR-0001](../adr/0001-unboxed-maybe-and-result.md).

### `map`/`andThen` reject `async` and thenable-returning callbacks

Same change as [`/maybe`'s](#mapandthen-reject-async-callbacks-at-compile-time),
same fix: nothing in `/result` can assert a value resolved
synchronously, so a callback whose return type has a thenable arm (a
`Promise`, a custom deferred, or a sync/async union like
`(n) => number | Promise<number>`) is a compile error. Lift with
`promise/resultify` or `call/resultify`, then compose with `.then()` —
every combinator's config-only form is a plain unary function, so it
already slots in:

```ts
// 0.1.0 — compiled; the "Success" was an unresolved Promise
const widget = map(async (id: number) => fetchWidget(id))(idResult)

// 0.3.0
import { fail, resultify } from '@lhellemons/ground-types/promise'
const widget = await resultify(fail, fetchWidget(id)).then(
  map((w: Widget) => w.label),
)
```

### `tryCatch`: handler shape, overload split, async rejection

Three changes, in ascending order of impact:

1. **`errorHandler` now returns a `Result<T, E>`, not an `E`.** This is
   backward compatible: `Failure<T, E>` is `E` intersected with optional
   compile-time-only phantoms, so every `Error` you already return _is_
   a valid `Result`. Existing handlers keep compiling unchanged. What it
   buys you is that a handler may now also **recover** — return a
   `Success` — using the same handler vocabulary as
   `promise/resultify`.

2. **Naming `E` without supplying a handler no longer compiles.**
   `tryCatch` is split into two overloads: `tryCatch(fn)` fixes
   `E = Error` (which is what the default handler can actually honour),
   and `tryCatch(fn, handler)` is generic in `E`. The old spelling —
   three type arguments, one value argument — let a thrown `TypeError`
   pass as `Failure<T, MyError>` via a documented unsound cast.

   ```ts
   // 0.1.0 — compiled, unsound
   const parse = tryCatch<Config, [string], ConfigError>(parseConfig)

   // 0.3.0 — supply the handler that produces the named error
   const parse = tryCatch(parseConfig, (e) => new ConfigError(String(e)))

   // 0.3.0 — or accept E = Error and drop the type arguments
   const parse = tryCatch(parseConfig)
   ```

3. **An `async` function is rejected at compile time.** An `async fn`'s
   throw happens after `tryCatch`'s `try`/`catch` has exited, so 0.1.0
   returned a "Result" that `isSuccess` reported `true` while the
   promise inside it rejected unhandled. Lift with `promise/resultify`
   instead:

   ```ts
   // 0.1.0 — compiled, rejected unhandled at runtime
   const fetched = tryCatch(async () => fetchWidget(id))()

   // 0.3.0
   import { fail, resultify } from '@lhellemons/ground-types/promise'
   const fetched = await resultify(fail, fetchWidget(id))
   ```

**Runtime behaviour change to be aware of:** in 0.1.0, `tryCatch(fn)`'s
default handler passed a thrown _non-Error_ value straight through — a
thrown string came back as a "Failure" that `isFailure` read as a
`Success`, the failure vanishing into the success channel. In 0.3.0 the
default handler wraps any non-`Error` throw in the new
`result/ThrownError` (the original value is preserved on its `.thrown`
property), so it is reported as the `Failure` it always was. A thrown
`Error` still passes through with its concrete subclass intact. If any
code relied on the old pass-through, it was relying on a bug — but it
is an observable change, so audit for it.

## `/brand`

### The brand key is a module-private `unique symbol` — check this even if nothing fails to compile

In 0.1.0, `Brand<B>` was `{ __brand: B }` — a plain string property, so
a hand-rolled cast anywhere in your codebase produced a value assignable
to the branded type, bypassing whatever validation the type stood for.
In 0.3.0 the key is a `unique symbol` private to the `brand` module: the
hand-rolled cast no longer produces an assignable value, and the brand
key no longer appears in `keyof` on a branded value.

This is the change most likely to break an 0.1.0 consumer **silently
at first**: the cast sites themselves don't error — the values they
produce just stop being accepted where the branded type is required.
Grep your codebase for `__brand`.

```ts
type Email = Branded<string, 'Email'>

// 0.1.0 — compiled, and bypassed validation
const email: Email = 'anything' as string & { __brand: 'Email' }

// 0.3.0 — cast to the branded type itself, inside a validating constructor
const Email = definePrimitiveValueObject<Email>((value) => {
  if (!value.includes('@')) throw new Error(`not an email: ${value}`)
  return value as Email // the sanctioned cast: value as T, post-validation
})
const email = Email('user@example.com') // throws on invalid input
const checked = Email.from('user@example.com') // Result<Email, Error>
```

The rule: `value as T` is legitimate _inside_ the validating
construction path (a `definePrimitiveValueObject` constructor, or your
own factory that validates first); a structural stand-in for the brand
is not, anywhere.

## `/value-object`

### `definePrimitiveValueObject` type parameters: `<P, T>` → `<T, P, E>`

The order is reversed to match `PrimitiveValueObject<T, P, E>`, `P` now
defaults to `string`, and a new defaulted `E` names the error type
`.from` can fail with. The common case is now a single explicit type
argument — the branded type you are actually defining:

```ts
// 0.1.0 — both named, primitive first
const Email = definePrimitiveValueObject<string, Email>(construct)

// 0.3.0 — the branded type first; P defaults to string
const Email = definePrimitiveValueObject<Email>(construct)

// 0.3.0 — non-string primitive: name both, T first
const Port = definePrimitiveValueObject<Port, number>(construct)
```

Beware the half-migrated form: `definePrimitiveValueObject<Email>(...)`
under the _old_ order also compiled — by binding `Email` to `P` and
leaving `T` as `unknown`. If you had written that, 0.3.0 silently makes
it mean what you meant.

### `.from` can now carry a concrete error type

`PrimitiveValueObject<T, P, E>` and `DomainObjectFactory<..., E, ...>`
gain an `E extends Error = Error` parameter, and
`definePrimitiveValueObject` takes an optional `errorHandler` to
translate a thrown value into that subclass — so `.from`'s failures can
be branched on by type instead of being flattened to plain `Error`.
Purely additive if you ignore it. When you use it, **name `E` explicitly
alongside `T`**: `Success`'s invariant `E` phantom keeps TypeScript from
reliably inferring `E` from the handler's return type alone
(see the docblock and [ADR-0001](../adr/0001-unboxed-maybe-and-result.md)'s
2026-08-04 amendment).

```ts
class InvalidEmail extends Error {}

const Email = definePrimitiveValueObject<Email, string, InvalidEmail>(
  (value) => {
    if (!value.includes('@')) throw new InvalidEmail(value)
    return value as Email
  },
  (e) => (e instanceof InvalidEmail ? e : new InvalidEmail(String(e))),
)

const result = Email.from('nope') // Result<Email, InvalidEmail>
```

## `/domain`

### `DomainObjectDTO` is now `DTOSource`

Same shape (`{ readonly dto: TDTO }`), same signature; only the name
changed — the old name claimed the type _was_ the DTO, when it is the
domain object's seam for recovering one. Rename the import and any
`implements`/`satisfies` clause:

```ts
// 0.1.0
import type { DomainObjectDTO } from '@lhellemons/ground-types/domain'
class User implements DomainObjectDTO<UserDTO> { ... }

// 0.3.0
import type { DTOSource } from '@lhellemons/ground-types/domain'
class User implements DTOSource<UserDTO> { ... }
```

### `DomainObjectFactory` gains `E` — ahead of `TExtra`

`DomainObjectFactory<TDomain, TDTO, TExtra>` is now
`DomainObjectFactory<TDomain, TDTO, E, TExtra>`, with `E` defaulted to
`Error`. A factory naming neither is unaffected; a factory that named
`TExtra` must now name `E` too, in third position:

```ts
// 0.1.0
type UserFactory = DomainObjectFactory<User, UserDTO, [Clock]>

// 0.3.0
type UserFactory = DomainObjectFactory<User, UserDTO, Error, [Clock]>
```

## `/fn`

### `Function` is now `Fn`

Same signature; the old name shadowed the global `Function` at every
import site.

```ts
// 0.1.0
import type { Function } from '@lhellemons/ground-types/fn'
const parse: Function<Config, [string]> = ...

// 0.3.0
import type { Fn } from '@lhellemons/ground-types/fn'
const parse: Fn<Config, [string]> = ...
```

`compose` is extended from exactly two Mappers to up to ten —
non-breaking; every existing 2-ary call typechecks and behaves exactly
as before. `/fn` also gains `Mapper`, `CurryableMapper`, `pipe`,
`curry`, `identity` and `constant` — see
[What 0.3.0 adds](#what-030-adds).

## `/intern-registry`

No breaking changes. `internByKey` is added — it interns a
`CompoundValueObject` under a key and throws if the created value's own
`key` disagrees. One subtle behaviour fix: `getOrCreate` now decides
"already interned?" with `Map.has` rather than an `!== undefined` test,
so a value legitimately interned _as_ `undefined` is no longer re-created
on every call.

## The currying retrofit — your existing call sites do not break

Every config-taking combinator in `/maybe` (`map`, `andThen`, `orElse`,
`fallback`) and `/result` (`map`, `mapError`, `andThen`, `orElse`,
`fallback`, `fromMaybe`) now _also_ accepts the value directly as a
second argument. This is purely additive: the curried form you have been
calling since 0.1.0 is still the first overload.

```ts
map(double)(maybe(x)) // 0.1.0 style — still compiles, still works
map(double, maybe(x)) // 0.3.0 — same result, applied immediately
```

Which shape a call is in is decided by arity, never by inspecting the
value — so `map(fn, nothing())` applies (`Nothing` _is_ `undefined`)
rather than handing back the mapper. See
[ADR-0003](../adr/0003-currying.md).

## What 0.3.0 adds

Nothing here requires action; it is listed so an upgrading consumer
knows what became available.

- **`maybe/fromNullable`** — folds both `null` and `undefined` to
  `Nothing`, returning `Maybe<NonNullable<T>>`. Use it at
  null-convention boundaries (`querySelector`, `exec`, JSON fields):
  `maybe()` itself is unchanged and treats **only `undefined`** as
  absent — to `maybe()`, a `null` is a value and becomes a `Just`.
- **`result/mapError`** — `map`'s dual over the failure channel:
  translate a `Failure`'s error (or recover) mid-chain instead of only
  erasing it at the end.
- **`result/orElse`, `result/fromMaybe`, `maybe/fallback`,
  `maybe/fromResult`, `maybe/assertJust`** (added in 0.2.0) — the
  combinator sets of the two modules now mirror each other, with a
  bridge each way.
- **`result/ThrownError`** — the wrapper a non-`Error` throw arrives in;
  the original value is on `.thrown`.
- **`Just`/`Nothing` default their type parameter to `unknown`**, so the
  case names can be written bare in annotations (`Maybe` still requires
  its argument, deliberately).
- **`fn` grows into the function vocabulary**: `Mapper`,
  `CurryableMapper`, `pipe` (value-first, up to ten steps, always
  immediate), `curry` (the extension point for writing your own
  curryable combinator), `identity`, `constant`, and a variadic
  `compose` (up to ten Mappers, right to left).
- **`intern-registry/internByKey`** — see above.
- **The asynchrony layer**: `/promise` (`AbortablePromise`, `State`,
  `resultify`/`fail`/`recoverWith`), `/promise/fake` (manually
  settleable test doubles, on a separate subpath so they cannot reach a
  production bundle), `/call` (`Call`, `AsyncCall`, `AbortableCall`,
  `abortable`, `resultify`), and `/abort` (`AbortError`,
  `isAbortError`, `ABORT_ERROR_NAME`). There is deliberately no
  `mapAsync` or `AsyncResult`: `resultify` turns a rejecting promise
  into one that always resolves with a `Result`, and every synchronous
  combinator composes with `.then()`. Abort propagates _upstream_ —
  read [ADR-0002](../adr/0002-abort-propagation.md) before wiring
  cancellation.
- **A root entry point**:
  `import { maybe, result } from '@lhellemons/ground-types'` now
  resolves, re-exporting each module as a namespace (`intern-registry`
  becomes `internRegistry`, `value-object` becomes `valueObject`).
  Per-module subpath imports remain the recommended style;
  `/promise/fake` is excluded from the root on purpose.
